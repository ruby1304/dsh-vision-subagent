# Contributing to dsh-vision-subagent

Thanks for helping give DeepSeek Harness agents eyes. This document covers the development loop; for usage see [README.md](README.md) ([中文](README.zh.md)).

## Setup

```sh
npm install
npm run typecheck   # tsc --noEmit
npm test            # vitest run
npm run build       # tsc -p tsconfig.build.json && tsdown (host lib/ + client bundle)
```

Node 22+ is required (matching the harness runtime). CI runs the same four commands on every push and PR.

## Try your changes in a live profile

The plugin is plain npm packaging; install your checkout into a dsh profile and it is loaded through a symlink:

```sh
dsh plugin --profile web add /path/to/your/checkout
# edit code, then:
npm run build
# restart dsh web to pick up host-side changes
```

The client bundle (`lib/client.js`) is rebuilt by `npm run build` (tsdown) and served on the next page load.

## Code conventions

- **No secrets, ever.** API keys live in the vision route's credential reference (environment variables); the plugin config schema accepts no key material, and nothing sensitive may reach logs or session events.
- **Containment is structural.** Paths reaching the disk are generated by the plugin (see `src/tool-fetch.ts`); user-controlled input is validated before any I/O.
- **Duck-typed harness services.** The plugin consumes `ctx.*` services through structural interfaces so it stays tolerant across harness rc versions. Runtime dependencies are only `@deepseek-ai/dsh-tools` and `@deepseek-ai/schemastery`.
- Every typed error carries a stable `VISION_*` code (`src/errors.ts`) — add a code instead of rewording messages.

## Tests

Pure logic (prompt assembly, chat projection, config) is unit-tested without harness services; tool behavior is tested against structural fakes (see `tests/tool-fetch.spec.ts`). Please add tests alongside behavior changes, and keep the durable wire formats (`src/web-contract.ts`) backward-compatible — old sessions must keep rendering.

## Submitting

1. Fork, branch from `main`, keep commits focused (`feat:` / `fix:` / `docs:` prefixes).
2. Update `CHANGELOG.md` and both READMEs when behavior or config changes.
3. Open the PR with a screenshot or session excerpt when the change is user-visible.
